## 2. 本课程采用的表示法

本节依据用户提供的课程约定，而不是将其误称为老师 PDF 中已有的逐字规定。

| 内容 | 当前 Chen 图的表示 |
|---|---|
| 实体 | 矩形 |
| 联系 | 菱形 |
| 属性 | 椭圆 |
| 主键 | 属性文字加下划线 |
| 基数上限为一 | 从联系菱形指向该实体的箭头 |
| 基数上限为多 | 不加箭头 |
| 完全参与（最少一） | 实体与联系之间双线 |
| 部分参与（可以零） | 实体与联系之间单线 |

箭头是基数约束，不是“业务流程先做谁”的方向。参与约束与基数约束共同表达 0..1、0..N、1 等含义，不再用单独的 1／N 数字替代课程箭头画法。

## 3. 十条联系怎样解释

| 联系 | 箭头指向 | 双线在哪端 | 含义 |
|---|---|---|---|
| User — places — Order | User | Order | 一笔订单只有一个购买会员；会员可以没有或有多笔订单 |
| User — makes — Booking | User | Booking | 一条预约只有一个会员；会员可以没有或有多条预约 |
| Order — selects — MembershipPlan | MembershipPlan | Order | 一笔订单只选一个套餐版本；一个版本可以尚未被买或被多次购买 |
| Order — has attempts — Payment | Order | Payment | 一次付款尝试属于一笔订单；一笔订单可没有或有多次尝试 |
| Order — creates — Membership | Order 与 Membership | Membership | 一个周期来自一笔订单，一笔订单最多产生一个周期；未付款订单可没有周期 |
| Booking — reserves — ClassSession | ClassSession | Booking | 一条预约只约一节具体课；场次可以尚无或有多条预约 |
| Booking — has result — Attendance | Booking 与 Attendance | Attendance | 一个结果对应一条预约，预约最多一个结果；尚未结算时可以没有 |
| ClassSession — instance of — Course | Course | ClassSession | 一次排课对应一个课程类型；类型可以对应多次排课 |
| ClassSession — taught by — Coach | Coach | ClassSession | 每场一个教练；教练可以没有或有多场安排 |
| ClassSession — held in — Venue | Venue | ClassSession | 每场一个场地；场地可以没有或有多场安排 |

其中两条一对一联系各有两支箭头，所以共有十二支基数箭头。共有十个完全参与端，分别使用两条平行线。

会籍的会员和套餐通过来源订单追溯；没有重新加入需要重复维护的会员／套餐直接关联。购买与付款、课程与场次、预约与出勤仍分别建模，未改变既有模型。

双线表示至少参与一个联系，但不能自动保证“已付款订单恰好创建会籍”。付款状态、重复请求、时间连续覆盖、容量与冲突等条件仍由原有业务约束说明，后续通过数据库与事务实现。

## 5. 对线条的修正

- 使用明确的节点位置及连接点，而不是自动布局后再叠加双线。
- 每一条关系连接均为直线段，不使用折线或曲线。
- 每个完全参与端的两条线相互平行，保持固定间距；遇箭头时在箭头底部结束，不相互穿过。
- 箭头位于实体端，方向由“该端最多一个”决定，与页面布局的左右顺序无关。
- 分开下方三个联系菱形，防止顶点相接被误读为额外联系。

## 8. 理解检查与下一步

**为什么 places 的箭头指 User，而不是 Order？**  
因为一笔订单最多对应一个 User；一个 User 可以有多笔 Order，订单端不画箭头。

**为什么 Order — Membership 两边都有箭头，却只有 Membership 端双线？**  
双方最多一条匹配，但未付款订单可以没有会籍，所以订单是部分参与；每个会籍都必须有来源订单，所以会籍完全参与。

**为何 ClassSession 在三个资源联系中都用双线？**  
本版规定每场必须有课程类型、教练和场地；各资源可以尚未安排场次，因此资源端用单线。
